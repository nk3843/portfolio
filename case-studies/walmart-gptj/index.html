    Enterprise LLM Fine-Tuning: GPT-J at Walmart

    The Problem

    HR support was overwhelmed. Walmart's HR team received 20,000+ employee queries daily across benefits, policies, leave requests, and payroll issues. The existing rule-based chatbot could only handle ~30% of queries accurately, routing the rest to human agents.

    Business impact: Long wait times, frustrated employees, and HR team burnout. We needed an AI solution that could handle complex, conversational queries while maintaining accuracy.

    The Constraint

    We couldn't use OpenAI's API due to data privacy regulations. Employee HR data (salaries, health info, performance reviews) is highly sensitive and cannot leave Walmart's infrastructure.

    The requirement: Fine-tune an open-source LLM on GCP within Walmart's compliance boundaries, achieving production-grade quality with 40%+ accuracy improvement.

    The Challenge

    Building a production LLM system from scratch meant solving multiple problems: - Scale: Fine-tuning a 6B parameter model on multi-TB HR datasets - Accuracy: Entity resolution for 500K+ employees, thousands of policies - Latency: Sub-second inference for 20K daily interactions - Reliability: Production deployment with monitoring and fallback systems

    The Solution

    Architecture Overview

    I architected a GPT-J (6B parameter) fine-tuning framework deployed on GCP, processing multi-TB HR datasets with PySpark and achieving production deployment with sub-second latency.

    The "Senior" Technical Details

    Challenge 1: Fitting 6B Parameters in GPU Memory

    Problem: GPT-J has 6 billion parameters (~24GB in FP32). Even with GCP's A100 GPUs (40GB), we couldn't fit the model + optimizer states + gradients + batch data in memory.

    Solution - Multi-pronged optimization strategy:

    1. DeepSpeed ZeRO Stage 2: Sharded optimizer states across GPUs, reducing per-GPU memory by 50% 

      # DeepSpeed configuration
{
  "zero_optimization": {
    "stage": 2,  # Shard optimizer states
    "offload_optimizer": {"device": "cpu"},  # Offload to CPU RAM
    "allgather_bucket_size": 5e8,
    "reduce_bucket_size": 5e8
  },
  "fp16": {"enabled": true}  # Mixed precision
}

    2. Gradient Checkpointing: Trade compute for memory by recomputing activations during backward pass instead of storing them

    3. Reduced activation memory by ~70%

    4. Increased training time by only ~20% (acceptable trade-off)

    5. LoRA (Low-Rank Adaptation): Instead of fine-tuning all 6B parameters, we injected trainable low-rank matrices

    6. Only 0.6B trainable parameters (10% of original)
    7. 90% reduction in GPU memory for gradients
    8. Minimal quality degradation vs full fine-tuning

    Result: Fit the entire training pipeline on 4x A100 GPUs with batch size of 32.

    Challenge 2: Data Pipeline at Multi-TB Scale

    Processing internal HR data (employee records, policies, support tickets, FAQs) across 10+ years:

    PySpark Pipeline (distributed across 20-node cluster): 

    # Conceptual - actual code simplified
training_data = (
    spark.read.parquet("hr_data_lake")
    .filter(col("year") >= 2018)  # Recent data only
    .join(policies, on="policy_id")
    .withColumn("prompt", create_prompt_udf(col("query")))
    .withColumn("completion", col("resolution"))
    .repartition(500)  # Distribute across workers
    .write.parquet("training_dataset")
)

    Data processing innovations: - Deduplication: Fuzzy matching to remove near-duplicate queries (reduced dataset by 40%) - Augmentation: Synthetic query generation for edge cases (increased coverage by 25%) - Quality scoring: ML-based filtering to remove low-quality support tickets

    Impact: Reduced preprocessing from 3 weeks to 2 days.

    Challenge 3: Production Deployment with Hot-Swapping

    Requirement: Zero-downtime deployment for model updates (weekly retraining).

    Solution - Blue/Green Deployment with GKE: 1. Deploy new model version to "green" cluster 2. Run shadow traffic (real queries, responses logged but not served) 3. Compare quality metrics (BLEU, entity accuracy) against "blue" production 4. Gradual traffic shift: 10% → 50% → 100% over 24 hours 5. Automatic rollback if error rate > 5%

    Monitoring stack: - Latency: P50, P95, P99 inference times (target: P95 < 800ms) - Quality: Daily BERT-score evaluation on random sample - Drift: Feature distribution KL-divergence vs training data

    Data Engineering Pipeline

    Built end-to-end data pipeline using PySpark to: - Process multi-TB datasets from internal HR systems (Workday, SuccessFactors, internal tools) - Clean and normalize employee records, policies, and FAQs - Generate high-quality training pairs with prompt engineering - Implement quality checks: duplicate detection, PII masking, data validation

    Impact metric: Reduced data preprocessing time from weeks to days with distributed Spark processing.
